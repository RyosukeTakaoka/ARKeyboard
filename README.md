# ARKeyboard — 膝(または机)をキーボードにする iPhone アプリ

iPhone の背面カメラで両手の指先を追跡し、iPad の分割キーボードのような配置で
「指で面を叩いた瞬間」を 1 文字の入力にするアプリです。
研究(TouchInsight、Acustico、Goodman ら、Gunawardana ら、VelociTap など)の考え方を、
iPhone の標準フレームワークで実現できる範囲で取り入れています。
比較実験として、片手の 12 キー**フリック入力**(かな)と、つまんだ指で書く**手書き入力**もあります。

- 対象: iPhone 実機、iOS 17 以上、SwiftUI
- 外部ライブラリ: なし(MediaPipe は任意。入れなくてもビルド・動作します)
- **手・音・動きのデータは端末の外に送信しません**(ネット通信のコードはありません。文字認識も端末内の Vision)
- すべての機能は設定画面のスイッチでオン・オフでき、記録データで「あり/なし」を比べられます

## 1. 実機での実行手順(署名・ビルド・許可ダイアログ)

### 必要なもの
- Mac(Xcode 16 以上。このプロジェクトは Xcode 16 の「フォルダ同期」形式です)
- iPhone(iOS 17 以上)と USB ケーブル
- Apple ID(無料のものでも実機で動かせます)

### 手順
1. Mac でこのリポジトリをクローンし、**`ARKeyboard.xcodeproj` をダブルクリック**して Xcode で開きます。
   (同じフォルダにある `Package.swift` はロジックのテスト用です。アプリは .xcodeproj から開いてください)
2. **署名の設定**: 左のナビゲーターで一番上の「ARKeyboard」(青いアイコン)を選び、
   TARGETS の「ARKeyboard」→ **Signing & Capabilities** を開きます。
   - **Team** で自分の Apple ID(Personal Team)を選びます。
     (Apple ID が出てこないときは、Xcode → Settings → Accounts で Apple ID を追加します)
   - **Bundle Identifier** の `com.example.ARKeyboard` を、自分だけの名前(例: `com.yourname.ARKeyboard`)に変えます。
     (`com.example` のままだと、他の人と重なって署名に失敗することがあります)
3. **実行先の選択**: iPhone を Mac につなぎ、Xcode 上部の実行先で自分の iPhone を選びます。
   - 初めての場合、iPhone の **設定 → プライバシーとセキュリティ → デベロッパモード** をオンにして再起動が必要です。
   - 「このコンピュータを信頼しますか?」と出たら「信頼」を押します。
4. **ビルドと実行**: ▶︎(Run)ボタンを押します。
   - 初回は iPhone 側で「信頼されていないデベロッパ」と出ることがあります。
     **設定 → 一般 → VPN とデバイス管理** で自分の Apple ID を「信頼」してから、もう一度 ▶︎ を押します。
5. **許可のダイアログ**(アプリの初回起動時に出ます)
   - **カメラ**(必須): 指先の追跡に使います。「許可しない」を押した場合は、
     設定アプリ → ARKeyboard → カメラ をオンにしてください。
   - **マイク**(推奨): 叩いた音で、タップの判定を正確にします(許可しなくてもカメラだけで動きます)。
   - **モーションとフィットネス**(机モードで「本体の振動」を使うときだけ): 机に置いた iPhone の振動を補助に使います。
   - いずれも理由の文(日本語)は `Config/Info.plist` に書いてあります。

### コマンドラインでのビルド確認(任意)
```sh
xcodebuild -project ARKeyboard.xcodeproj -scheme ARKeyboard \
  -destination 'generic/platform=iOS' -configuration Debug build CODE_SIGNING_ALLOWED=NO
```

### シミュレーターでは?
シミュレーターにはカメラが無いため、「実機で実行してください」と表示されます(クラッシュはしません)。

### ロジックのテスト(iPhone が無くても実行可能)
```sh
swift test    # Mac のターミナルで、リポジトリのルートで(113 個のテスト)
python3 -m unittest discover -s tools/eval   # 評価指標のテスト
```

## 2. 使い方

1. **iPhone の置き方**: iPhone を手の上にかざすように固定し、背面カメラで両手が画面に収まるようにします
   (画面は自分の方を向く)。スタンドやアームで固定するのがおすすめです。
2. 画面下の **「キャリブレーション」** を押し、両手をホームポジション
   (左: A S D F、右: J K L ;。親指はスペース)に置いて **2 秒静止** します。
3. 半透明のキー配置が表示され、指先の下のキーが光ります。指で面を「トン」と叩くと入力されます。
4. 画面下のボタン:
   - スライダー: 感度(右ほど小さなタップにも反応)
   - 赤い丸: 記録モード(評価用のデータを集める)
   - 帽子: 練習モード(お題・正解率・速さ)
   - てんとう虫: デバッグ表示(速度グラフ・音の波形・FPS・タップログ・追跡器の比較)
   - 歯車: 設定(すべての機能のオン・オフとしきい値)
5. 重ねる表示(設定 → 表示): 「キー」「当たり判定」(言語モデルで広がる当たり判定の地図)「ヒートマップ」(実際に押した場所)

### 膝モードと机モード
| | 膝モード | 机モード |
|---|---|---|
| キーの大きさ | 1.15 倍 | 1.0 倍 |
| キー配置の基準 | 手に追従(脚が動いてもずれにくい) | 面に固定(実物のキーボードに近い) |
| タップの判定 | ゆるめ(布や脚はやわらかく止まり方がゆるい) | 厳しめ |
| 机の登録(ホモグラフィー) | 使わない(膝は平らでない) | 使える(奥が小さく映るゆがみを直す) |

**机の登録**(机モード、設定 → 机モード): 人差し指の先で、机の「奥の左 → 奥の右 → 手前の右 → 手前の左」を
順に 0.8 秒ずつ押さえます(9 点モードなら 3×3 の 9 か所)。画面をタップして登録する方法も選べます。

### 入力方式(設定 → 入力方式)
| 方式 | 使い方 |
|---|---|
| QWERTY(英字) | 両手で分割キーボード。親指でスペース。画面のボタンで削除・改行 |
| フリック(かな)| 利き手の人差し指の周りに 12 キー。キーの上で一瞬止めてから、方向へ素早く動かす(あ段は空中で軽く叩く)。もう一方の手は機能パッド(親指=空白、人差し指=゛゜小、中指=削除、薬指=改行、小指=次の候補。設定で変更可)。方式A(空中)と方式B(面に触れて音で始まりを判定)を選べる |
| 手書き | 書く手の親指と人差し指をつまんだまま書き、離して 1 秒たつと文字を認識(Vision、日本語)。もう一方の手は機能パッド |

## 3. うまく動かない時の確認項目

| 症状 | 確認すること |
|---|---|
| 「実機で実行してください」と出る | シミュレーターで動かしていないか |
| ビルドで署名のエラー | Team を選んだか/Bundle Identifier を自分の名前に変えたか |
| iPhone に入らない・起動しない | デベロッパモード/「VPN とデバイス管理」で信頼したか |
| 「カメラへのアクセスが許可されていません」 | 設定アプリ → ARKeyboard → カメラ をオン |
| 手の骨格(点と線)が出ない | 明るい場所か/手が画面に入っているか/手のひらを下にしているか |
| 左右の色が逆(左手がオレンジ) | 設定 → キー配置 → 「左右の手を入れ替える」 |
| キャリブレーションが終わらない | 両手の指先がすべて見えているか(案内の文を確認)/2 秒間動かさない |
| キーの位置がずれていく | 机モードなら iPhone や机が動いていないか(動いたら再キャリブレーション)/膝モードは「手に追従」 |
| 叩いても入力されない | デバッグ表示のタップログを見る。「音なし」なら設定のマイクの状態・音の感度 k・時間窓を確認。ログに何も出ないなら感度を上げる |
| 叩いていないのに入力される | 感度を下げる/「音の立ち上がりを条件にする」をオン |
| 同じ文字が 2 回入る | クールダウンを長く |
| 隣のキーになる | 再キャリブレーション/キーの大きさ/「指の担当キーだけから選ぶ」をオン/当たり判定の表示で確認 |
| 触覚が来ない | 設定 → フィードバック/iPhone 本体の「サウンドと触覚」 |
| FPS が低い(20 未満) | 明るい場所で使う/ほかのアプリを閉じる/デバッグ表示を切る |
| フリックが反応しない | キーの上で一瞬(0.1 秒)止めてから動かす/設定 → フリック → 「動き出しの速さ」を下げる |
| キーへの移動がフリックになる | 移動をゆっくりに/「動き出しの速さ」を上げる |
| フリックの方向がいつも少しずれる | 設定 → 個人適応をオン(指ごとの回転のずれを学習) |
| 手書きの文字が鏡文字・横倒しで認識される | 設定 → 手書き → 「左右反転」。手首→指先の向きが「上」になる |
| 手書きでペンが勝手に上がる・下りる | 設定 → 手書き → 「ペンを下ろす距離・上げる距離」 |
| 机の登録が進まない | 指先を 0.8 秒、ほとんど動かさずに押さえる/右手の人差し指で行う |

## 4. タップ判定のしきい値の調整方法

タップは「指先が**手のひらに対して**素早く下りて(手首の方向へ動いて)、**急に止まった**瞬間」です。
加えて(マイクを使う場合)、その前後に**叩いた音**があることを条件にします(タップ推定レベルA)。

### 手順
1. 画面下のてんとう虫でデバッグ表示を出し、グラフのメニューで調整したい指(例: 右手の人差し指)を選びます。
2. その指で何回か叩き、グラフを見ます。
   - **白い線** = 下向きの速さ、**赤い点線** = しきい値、**黄色の点** = 下ろし中、**緑の縦線** = タップと判定
3. 状況に応じて調整します(設定 → タップ判定):

| 見えている状態 | 調整 |
|---|---|
| 叩いても白い線が赤い点線を超えない | 感度を上げる、または「下ろす速さのしきい値」を下げる |
| 黄色の点は出るのに緑の線が出ない(止まりを検出できない) | 「止まりの判定(ピーク比)」を上げる/「平滑化」を下げる |
| 指を動かしただけで緑の線が出る | 感度を下げる/「最小の移動量」を上げる/音の条件をオン |
| 1 回で 2 回入る | 「クールダウン」を長く |
| 隣の指がつられて入る | 「同じ手の別の指のロック」を長く |
| 手ごと動かすと入る | 「手全体の動きの上限」を下げる |

4. 音の条件(レベルA)の調整: タップログの「音±○ms」を見て、ほとんどが時間窓(初期値 −100〜+60 ms)に
   入るよう、設定 → センサーと二重条件 の時間窓を合わせます。音の波形グラフでは、赤い縦線(音)と
   緑の縦線(カメラのタップ)が近くに並んでいれば正常です。
5. 調整したら、記録モードでデータを取り、`tools/eval/evaluate.py` で「前より良くなったか」を数字で確認します(8 章)。

すべての初期値は `ARKeyboard/Core/KeyboardSettings.swift` の `applyModeDefaults`(タップ)と、
`ARKeyboard/Core/Flick.swift` の `FlickConfig`(フリック)、`ARKeyboard/Core/Handwriting.swift`(手書き)にあります。

### 合成データでの評価の要点(⚠️ 実際の性能ではありません)

人工的に作った手の動きによる結果なので、「どの機能がどの種類の誤りに効くか」の見通しとしてだけ読んでください。

- **音の二重条件**が最も効く: カメラだけでは、キーへの移動の途中の速い動きを誤ってタップにする(適合率 約 65〜75%)。
  音を条件にすると適合率が 97〜100% になり、文字誤り率(CER)が 34〜65% → 7〜16% に下がる(`docs/results.md`)
- **言語モデル**は、学習データに無い英文でも CER を少し下げる。**個人適応**は「指ごとに押し癖がある」データで効く
- **フリック**: ぶれが小さいとき、方式A(空中)の CER は約 2%。ただし関節点のぶれ(手の大きさの 1〜2%)に弱く、
  音で始まりを決める**方式B のほうがぶれに強い**(`docs/results-flick.md`)。QWERTY は音の条件のおかげで検出が崩れにくい
- **机の登録**: 指先で押さえて平均すると、画面タップより誤差が約 3〜4 割小さい見積もり(`docs/results-homography.md`)

### 見送ったこと(理由)

| 項目 | 理由 |
|---|---|
| Apple Watch の加速度を使う | Watch アプリ(別ターゲット)と WatchConnectivity が必要で、iPhone との通信の遅れがタップの時間窓(約 0.16 秒)より大きいおそれがある。iPhone 単体で完結する範囲を優先し、手首センサーの役割はマイクの音で代替した |
| 仮名漢字変換 | 使えそうな辞書(Mozc など)のライセンス条件を、この作業環境から確認できなかった。ひらがな入力と候補の表示まで |
| 青空文庫などの大きなかなコーパス | この環境からダウンロードできず、利用条件も未確認。自作のひらがな文で代替し、差し替え用のスクリプト(`tools/lm/romaji_to_kana.py`)を用意 |
| Acustico の TDOA による位置推定 | 約 1 MHz のサンプリングと手首の複数センサーが必要 |
| VibKeyboard の振動のフィンガープリント | CoreMotion の加速度は約 100 Hz で周波数の特徴が取れない |
| TouchInsight の Transformer-XL | 大量の正解付きデータと 3D の手追跡が前提。小さな MLP(レベルB)に置き換えた |
| クラウドとのハイブリッド | 手のデータを端末外に送らない方針のため |
| 接地面積 | カメラでは取れない。代わりに指先の動きの履歴・速さ・移動量をレベルB の特徴量に、LiDAR の高さを接触の確認に使った |

## 6. まだ確認できていないこと

**この作業は Linux の環境で行ったため、Xcode でのビルドと iPhone 実機での動作は一度も確認できていません。**
(確認できたことは 13 章を参照)

- **ビルド**: `xcodebuild` での iOS 向けビルド、SwiftUI の画面の表示(構文チェックのみ)
- **実機の動作**: カメラ・Vision の手の追跡の速さ(FPS)と、関節点のぶれの大きさ。
  特にフリックはぶれに弱いので、デバッグ表示の「追跡器の比較」のぶれの値が重要
- **時刻の基準**: カメラの撮影時刻・マイクの時刻(AVAudioTime の hostTime)・CoreMotion の時刻が、
  同じ「端末起動からの秒数」でそろっているか(そろっていないと、音の二重条件の時間窓がずれる)
- **しきい値**: すべての初期値は合成データと一般的な指の速さからの推定。とくにフリックの切り出しのしきい値は
  合成データを見ながら決めたので、合成データの評価は実力より良く出ている可能性が高い
- **MediaPipe**: CocoaPods で入れたビルド、左右の判定の入れ替え(鏡像の前提)が正しいか
- **LiDAR**: ARKit の深度のフレームと手の関節点の位置合わせ
- **手書き**: Vision の文字認識(紙の手書き・印刷文字向け)が、空中で書いた崩れた文字をどのくらい読めるか
- **レベルB**: 同梱していない(合成データで学習したモデルは `tools/eval/models/` に評価用として置いただけ)
- **調査**: 多くの資料はこの環境から読めず「未確認」としている(読めたのは Goodman らと Gunawardana らの論文のみ。
  各社の内部の数値は仮説扱い。`docs/research/README.md`)
- **評価の数値**: すべて合成データ。実際の利用者のデータは 1 件も無い

## 7. 次にやるべき 3 つのこと

1. **実機でビルドして、記録データを集める。**
   Xcode で実機に入れ(1 章)、12 章のチェックリストを確認したあと、記録モードで
   「キー(QWERTY)」「フレーズ」「仮名(フリック)」をそれぞれ数百回ずつ記録します。
   `python3 tools/eval/evaluate.py recordings/*.json` と `evaluate_flick.py` で、合成データの表を実データの表に置き換えます。
   同時に、デバッグ表示で関節点のぶれの大きさと、音とカメラの時刻のずれ(タップログの「音±○ms」)を測ります。
2. **実データでしきい値とモデルを合わせ直す。**
   タップの時間窓・速さのしきい値、フリックの方式A/B の選択(ぶれが大きければ B)、言語モデルの重みを、
   評価ツールの数字を見ながら決めます。レベルB のモデルを `tools/eval/train_levelb.py` で自分の記録から学習し、
   `ARKeyboard/Resources/Model/` に入れて、ルールだけの場合と比べます。
3. **言語モデルを大きくする。**
   今の言語モデルは自作の小さな文章(英語 約 7 千文字、ローマ字 約 4.5 千文字、かな 約 6.5 千文字)です。
   ライセンスを確認できる大きなコーパスに差し替えると、デコーダーの効き目が大きくなる見込みです
   (Python の参照実装 `tools/lm/ngram.py` とゴールデンテストで、Swift 版と同じ結果になることを確認できます)。

## 8. 記録と評価(データで比べる)

「機能を足したら本当に良くなったか」を数字で比べるための仕組みです。

1. **記録**: 画面下の赤い丸 → 課題(キー・フレーズ・仮名)を選ぶ → 表示された文字を打つ。
   関節の座標・音の特徴・加速度・目標の文字が JSON で保存されます(**映像と音そのものは保存しません**)。
2. **Mac へ送る**: 設定 → 記録データ → 共有ボタン(AirDrop)、または「ファイル」アプリ → このiPhone内 → ARKeyboard → Recordings。
   リポジトリの `recordings/` フォルダに置きます(`.gitignore` 済み)。
3. **評価**(Mac のターミナルで、リポジトリのルートで):
   ```sh
   swift build -c release --product arkeyboard-replay   # 初回だけ
   python3 tools/eval/evaluate.py recordings/*.json            # QWERTY → docs/results.md
   python3 tools/eval/evaluate_flick.py recordings/kana-*.json # フリック → docs/results-flick.md
   python3 tools/eval/evaluate.py --synthetic                  # 記録が無いときの動作確認(合成データ)
   swift run -c release arkeyboard-replay desk-accuracy        # 机の登録方法の誤差の見積もり
   python3 tools/eval/train_levelb.py recordings/*.json --out ARKeyboard/Resources/Model/   # レベルB の学習
   ```
   再生コマンドは、アプリと**同じ Swift のコード**で記録を判定し直すので、評価とアプリの動きが一致します。

| 結果のファイル | 内容 |
|---|---|
| `docs/results.md` | QWERTY: 機能の組み合わせごとの適合率・再現率・キー正解率・CER・WPM、ぶれへの強さ、言語モデルの重み |
| `docs/results-flick.md` | フリック: 方式A/B、方向の個人適応、方向の混同行列、QWERTY との比較(ぶれ)、かな言語モデルの重み |
| `docs/results-homography.md` | 机の登録方法ごとのキーの位置の誤差(仮想カメラでの見積もり) |

**現在の 3 つのファイルは、すべて合成データ・仮想カメラによる結果です(実際の性能ではありません)。**

## 9. 仕組みの概要とファイル構成

```
カメラ(AVFoundation / LiDAR機は ARKit)
  → 手の追跡(HandTracker: Vision。MediaPipe も差し替え可能)
  → 左右の割り当て・手の座標系(HandFrame)・机モードはホモグラフィー
  → キャリブレーション(Calibrator)・キー配置(KeyLayout / フリックは FlickModel)
  → タップ候補(TapDetector: 相対速度 + 急停止)/ フリックの切り出し(FlickSegmenter)/ 手書き(HandwritingRecorder)
  → センサー融合(SensorFusion: 音のオンセット・振動・LiDAR)= タップ推定レベルA(+ レベルB の学習モデル)
  → TouchEvent(いつ・どの指・どこ・確からしさ)
  → デコーダー(TapDecoder: 空間タッチモデル × 指の制約 × 文字 n-gram × 個人辞書、アンカー)
    → 単語単位のビームデコード / フリックはかなのビームデコード
  → 入力・触覚・音・記録・個人適応
```

**画像の上下左右は使いません**: キーの配置・フリックの方向・手書きの向きは、すべて「手首 → 中指の付け根 = 前」
「人差し指の付け根の側 = 親指側」で決めた手の座標系で計算します。iPhone をどの向きから手に向けても同じように動きます
(Vision の座標の変換は `Core/CoordinateConverter.swift` のコメントに詳しく書いてあります)。

| フォルダ | 内容 |
|---|---|
| `ARKeyboard/Core/` | 画面にもカメラにも依存しないロジック(`swift test` でテスト可能) |
| `ARKeyboard/Camera/` | カメラ・手の追跡(AVFoundation, Vision, ARKit, MediaPipe)、Core ML、手書きの文字認識 |
| `ARKeyboard/Sensors/` | マイク(AVAudioEngine + Accelerate)・加速度(CoreMotion) |
| `ARKeyboard/ViewModel/` | 画面とロジックの橋渡し、保存、触覚・音 |
| `ARKeyboard/Views/` | SwiftUI の画面 |
| `ARKeyboard/Resources/Corpus/` | 言語モデルの学習用テキスト(このリポジトリのために自作) |
| `ARKeyboard/Resources/Model/` | レベルB のモデル・MediaPipe のモデルを置く場所(最初は空) |
| `Tests/ARKeyboardCoreTests/` | 単体テスト(Python 版とのゴールデンテストを含む) |
| `tools/replay/` | 記録の再生・合成データ作り・机の誤差の見積もり(Swift のコマンド) |
| `tools/eval/` | 評価ツール・レベルB の学習(Python) |
| `tools/lm/` | 言語モデルの Python 参照実装、ローマ字 → かな変換 |
| `docs/research/` | 論文・資料の調査メモと実現可能性の判断 |
| `docs/results*.md` | 評価結果(自動生成) |

### 言語モデルの学習データの出所
- `ARKeyboard/Resources/Corpus/corpus_english.txt`(約 7 千文字)と `corpus_romaji.txt`(約 4.5 千文字)は、
  **このリポジトリのために新しく書いた文章**です(既存の文章の転載ではないので、著作権の問題はありません)。
- `corpus_kana.txt`(約 6.5 千文字)は、`corpus_romaji.txt` を `tools/lm/romaji_to_kana.py` でひらがなに変換したものです。

  (言語モデルの効果を公平に測るため。かなは 10 文字以上の並びが学習データと重ならないことを確認済み)。
- 規模が小さいため、大きなコーパスに比べると予測は弱めです(7 章の 3)。

## 10. MediaPipe の導入手順(任意)

入れなくてもアプリは Vision で動きます。Vision と比べたいときだけ行ってください。

1. CocoaPods を入れる(ターミナルで `sudo gem install cocoapods`)
2. リポジトリのルートの `Podfile.example` を `Podfile` という名前でコピーし、そのフォルダで `pod install`
3. 以後は **`ARKeyboard.xcworkspace`** を開く(.xcodeproj ではなく)
4. 学習済みモデル `hand_landmarker.task` を Google の公式ページ
   (https://ai.google.dev/edge/mediapipe/solutions/vision/hand_landmarker/ios)からダウンロードし、
   `ARKeyboard/Resources/Model/` に置く
5. アプリの 設定 → 手の追跡 → MediaPipe を選ぶ。デバッグ表示の「追跡器の比較」で、FPS・処理時間・両手がそろう割合・ぶれを比べられる

MediaPipe の左右の判定は「自撮り(鏡像)の画像」を前提にしているため、背面カメラでは左右を入れ替えて使っています(実機で要確認)。

## 11. 置いた仮定(すべて)

**置き方・座標**
- iPhone を手の上にかざし、背面カメラで手の甲側(手のひらを下)を見る置き方を想定。
  この置き方では、指を下ろすと指先は画像上で「手首の方向」に動いて見えるので、タップの向きの初期値を「手首の方向」にした
  (設定で「画面の下方向」「向きを問わない」に変更可)。
- 画面は縦向き固定。背面カメラの画像は `.right` の向きとして Vision に渡す。
- 手書きの向き: カメラが手の甲側から見ていれば、「前を時計回りに 90 度 = 右」で左右が正しくなる。手のひら側から見ると鏡文字になる(設定の左右反転で対応)。

**時刻**
- カメラの撮影時刻(CMSampleBuffer)、マイクの時刻(AVAudioTime の hostTime)、CoreMotion の時刻は、
  すべて「端末起動からの秒数」で同じ基準と仮定(実機での確認が必要)。

**しきい値・モデルの数値**(すべて仮説。記録データで調整する前提)
- タップ: 膝モードは判定ゆるめ・机モードは厳しめ。クールダウン 約 150 ms、候補どうしの最短間隔 0.06 秒。
- 音の二重条件の時間窓: カメラのタップの 0.10 秒前〜0.06 秒後(音の処理の遅れとカメラの遅れの差を見込んだ値)。
- キャリブレーション: 2 秒静止(6 フレームの平均で静止を判定)。キー間隔 = 隣の指先どうしの平均距離。
  段の間隔 = キー間隔 × 見かけの縮み(手のひらの幅 ÷ 長さから推定)。
- デコーダー: 言語モデルの重み 0.4、キーごとのばらつき・アンカーの大きさ・入力速度への適応は既定値。
- フリック: 動き出し 2.0 手/秒、止まり 0.8 手/秒(0.03 秒続いたら)、静止 0.08 秒、距離 0.1 手以下はタップ、
  方向の鋭さ κ=3、方式B は接触から 0.25 秒で終わり・物音の除外は 1.8 手/秒。
  キーの上への移動は「ゆっくり(平均 1 手/秒程度)」と仮定(速い移動はフリックと区別できない)。
- 個人適応: 指×キーのずれを縮小推定、ずれの上限あり。個人辞書: 混ぜる重みの上限 0.3、英字とかな各 5000 文字まで。
- 手書き: つまみの距離 0.25 手でペンを下ろし 0.38 手で上げる、1 秒で書き終わり。
- 机の登録の誤差の見積もり: 画面タップ σ=10 ピクセル、関節点のぶれ σ=4 ピクセル、指先と触れた位置のずれ σ=2 mm。

**機能の既定のオン・オフ**
- オン: 音の二重条件、デコーダー、言語モデル、個人辞書、机の登録(机モード)。
- オフ: 単語単位のデコード(合成データで効果が小さかった)、個人適応(学習データが無い最初は効かない)、
  レベルB(モデルを入れたときだけ)、本体の振動、フリックの One Euro フィルター(合成データでは一長一短)。

**データ**
- 言語モデルは自作の小さな文章で十分に「効き目の向き」を確認できる、と仮定(大きさは 7 章の 3)。
- 合成データ(人工的な手の動き)は評価ツールの動作確認と見通しのためのもので、性能の根拠にはしない。
- 調査で読めなかった資料の数値(Gboard・SwiftKey・Apple・Samsung などの内部の値)は使わず、仮説として扱う。
